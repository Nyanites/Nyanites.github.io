Part 1 · Executive brief

The short version

PHP runs a large share of the web: corporate sites, customer portals, WordPress and e-commerce stores. A newly disclosed flaw in the PHP engine can let an attacker run their own commands on a web server without logging in.

The unusual part is that this isn't a mistake in anyone's website code. It sits in the software underneath, so a site your developers wrote perfectly is still exposed if the server runs an old PHP version. Patching the engine is the fix. Rewriting the website isn't.

9.2 / 10Severity score (CVSS 4.0). Rated critical.
No loginAn attacker needs no account or credentials.
All PHP appsEvery site on an unpatched server is affected, whatever its code quality.
Patch = fixThe only complete fix is updating PHP. Workarounds only reduce the risk.

What it means for the business

  • Data exposure. Even a failed attack can leak scraps of other visitors' data from server memory. A successful one hands over the server.
  • Downtime. Attack attempts tend to crash web workers, so customers may see errors and slow pages before anyone sees a breach.
  • Hidden inventory. PHP often runs on forgotten marketing sites, vendor-hosted portals and old internal tools. Those systems are the hardest to patch and the easiest to miss.
The good news

The attack is technically difficult to pull off reliably, and attempts are noisy: they crash things in recognisable ways. That gives defenders a window and a clear signal to watch for, which is what the tooling below is for.

What we did

We built an isolated lab with two deliberately unpatched PHP servers and used it to develop and test the detection side of this vulnerability. We wrote no attack code. The lab answers two questions every security team gets asked: are we exposed? and can we prove the fix worked?

Three decisions for this week

  1. Authorise an emergency PHP patch window for internet-facing systems first, then internal ones. This is the only real fix.
  2. Ask for a complete PHP inventory, including third-party and vendor-hosted sites. The fleet scanner below produces this list in minutes.
  3. Turn on crash alerting for web servers until patching is done. Repeated PHP crashes are the clearest early warning of an attack.

The rest of this page is written for the team that will carry those out.

Part 2 · Technical deep-dive

Root cause: stale global state across requests

CVE-2026-109619 (php-src advisory GHSA-6wmf-4rv5-p3rp, CVSS 4.0 9.2, CWE-416) is a heap use-after-free in the interpreter.

Persistent SAPIs (mod_php, PHP-FPM) reuse worker processes across requests. Some engine-global state (error, session, object and extension bookkeeping) can still point into the previous request's heap after that request has ended and its memory has been released. If the stale state is touched before request initialisation resets it, the worker dereferences freed memory. That causes memory disclosure at best, and code execution as the web-server user at worst.

Because the bug is in the engine, application code is irrelevant to exposure. Exposure depends on the PHP build plus the reachable trigger features, which is why the lab has no "vulnerable app". It runs an unpatched engine with the trigger settings on.

Detection in four layers

There's no fixed exploit byte signature for a memory-corruption race, so these detections focus on exposure (what can be hit), preconditions (what an attacker must do to set it up) and side effects (what a failing exploit leaves behind).

Layer 1 · Exposure

Fleet scanner

Remote PHP version fingerprint, checked against the fixed builds. Answers "where are we exposed?"

Layer 2 · Posture

Host check

Runs on the server itself. Reports version and trigger settings, and tells "mitigated" apart from "patched".

Layer 3 · Network

Suricata rules

Flag setup patterns: upload-progress bursts, repeated oversized POSTs and 500 storms.

Layer 4 · Logs

SIEM queries

Worker segfaults, the highest-fidelity signal, correlated with the network patterns.

Layer 1: Fleet exposure scanner

scan_fleet.py is a Python 3 script with only standard-library dependencies. It reads the PHP version from X-Powered-By, falls back to Server and then the HTML body, and classifies each host as AFFECTED, EOL, PATCHED or UNKNOWN. Exit codes are designed for CI or a scheduled job.

Know the blind spot

Hardened servers set expose_php=Off and hide the version. Those hosts come back UNKNOWN, not clean. Follow up with Layer 2 or your package inventory. Evidence: scan-before.csv · scan-after.csv.

Layer 3: Network rules (Suricata)

php2shell.rules holds three heuristic rules in the local SID range 1026001–1026003. Treat them as tunable starting points, not turnkey IOCs. SID 1026003 in particular will fire on any noisy app until you baseline it.

SIDDetectsDefault threshold
1026001Burst of POSTs carrying PHP_SESSION_UPLOAD_PROGRESS (109619 grooming)30 from one source in 10s
1026002Repeated POSTs declaring Content-Length ≥ 8 MB (109618 OOM pattern)10 from one source in 15s
1026003HTTP 500 storm from a PHP host (crash side effect)20 to one client in 10s
View the rules 
alert http any any -> $HOME_NET any ( \
    msg:"PHP2SHELL CVE-2026-109619 upload_progress field burst (possible UAF grooming)"; \
    flow:to_server,established; http.method; content:"POST"; \
    http.request_body; content:"PHP_SESSION_UPLOAD_PROGRESS"; nocase; \
    threshold:type both, track by_src, count 30, seconds 10; \
    classtype:attempted-admin; sid:1026001; rev:2; )

alert http any any -> $HOME_NET any ( \
    msg:"PHP2SHELL CVE-2026-109618 repeated oversized POST (possible memory_limit bailout abuse)"; \
    flow:to_server,established; http.method; content:"POST"; \
    http.content_len; pcre:"/^(?:[89][0-9]{6}|[0-9]{8,})$/"; \
    threshold:type both, track by_src, count 10, seconds 15; \
    classtype:attempted-dos; sid:1026002; rev:2; )

alert http $HOME_NET any -> any any ( \
    msg:"PHP2SHELL possible exploitation side effect: HTTP 500 burst from PHP host"; \
    flow:to_client,established; http.stat_code; content:"500"; \
    threshold:type both, track by_dst, count 20, seconds 10; \
    classtype:web-application-attack; sid:1026003; rev:2; )

On an internet-facing sensor, scope the inbound rules to $EXTERNAL_NET any -> $HOME_NET.

Layer 4: Log and SIEM detections

Network rules show attempts. Logs show consequences. A healthy PHP fleet almost never segfaults a worker, so a spike in segfaults is the strongest single indicator. Full query set: log_detections.md.

# mod_php (Apache error_log)
grep -E "child pid [0-9]+ exit signal Segmentation fault \(11\)" /var/log/apache2/error.log

# PHP-FPM
grep -E "child [0-9]+ (exited on signal 11|SIGSEGV)" /var/log/php*-fpm.log

# Splunk-style: segfaults per host per minute
index=web ("exit signal Segmentation fault" OR "exited on signal 11")
| bin _time span=1m | stats count by host, _time
| where count > 3
The page-worthy alert is a correlation

An attempt signal (upload-progress burst, OOM-fatal burst, or SID 1026001/1026002) plus a crash signal (worker segfault) from the same host within 5 minutes. That pairing is very unlikely to be benign.

Remediation

  1. Upgrade to 8.2.35, 8.3.36, 8.4.27 or 8.5.12 (or later). This is the only complete fix.
  2. If you can't patch yet, set session.upload_progress.enabled=0, and on 8.5 also set fatal_error_backtraces=0. Then restart every worker: the settings only apply to new workers. These steps reduce the exposure but don't remove it.
  3. Verify: check_mitigations.sh should exit 0 on each host, the fleet scan should exit 0, and segfault counts should return to baseline.
  4. Retire PHP ≤ 8.1. There is no full upstream fix for those branches.

Scope and limitations

  • No exploit is published here, on purpose. The lab demonstrates exposure and patch verification, which is the deliverable defenders need.
  • The network rules are heuristics. They catch setup patterns and side effects, not the corruption itself. Tune thresholds to your traffic.
  • Version fingerprinting can't see hosts with expose_php=Off, and some vendors backport fixes without changing the version string. Confirm with the vendor's package changelog.
  • Version data comes from the php-src advisory. Check php.net for updates before acting on it.
